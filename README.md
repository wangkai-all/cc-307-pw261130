# 检查排程台 (虚构演示)

一个从零实现的检查预约排程分析 Web 应用：事件溯源资源台账、排程计算、方案确认与回放。
**全部机构、设备、人员、检查均为虚构数据，只做运营排程分析，不提供任何医疗诊断、临床建议或真实预约服务。**

- 后端：Python 3.11 标准库（`http.server`），无第三方运行依赖
- 前端：原生 HTML/CSS/JS，无需构建
- 测试：`unittest`（后端 + HTTP 接口），Playwright（浏览器端到端，可选）

## 运行

```bash
python3 -m app.server --port 8000
# 打开 http://127.0.0.1:8000
```

可选环境变量：

| 变量 | 说明 | 默认 |
| --- | --- | --- |
| `SCHEDULE_DATA` | 台账与试算数据的存放目录 | `./data` |
| `PORT` / `HOST` | 监听端口 / 地址 | `8000` / `127.0.0.1` |
| `SCHEDULE_ALLOW_RESET` | 设为 `0` 关闭「重置演示」 | 开启 |

首次启动会自动写入虚构演示数据（19 个资源、6 个模板、72 项检查、5 天班次与前三天初始排班）。
数据只是两个目录：`data/ledger.jsonl`（正式事件台账）与 `data/trials/*.json`（试算）。

## 页面流程

1. **选择日期** — 顶部日期条，右侧资源台账与当日时间线随之切换。
2. **插入检查** — 从「可插单池」加入加急/补做检查，或使用自定义插单表单。
3. **运行试算** — 选择「整体优化」或「滚动局部调整」（可拖动顺延邻域），选择取舍目标（均衡 / 资源公平 / 少改期），可「3 人并行试算」对比。
4. **查看冲突** — 无法满足时，未排检查逐条给出具体原因（缺设备/缺班次/窗口不足/人员已满），不会塞进不合法时段。
5. **确认方案** — 服务器逐项核对资源版本、检查签名与方案合法性，通过后才写入正式台账；不通过则逐条返回拒绝原因。
6. **回放** — 「确认与回放」按事件序号拖动即可看到任一时点的当日状态；「事件台账」展示正式记录与恢复/隔离状态。

执行操作（开始 / 完成 / 爽约 / 取消、设备故障、班次调整）在检查详情与资源台账中，均以追加事件记录。

## 设计要点

### 事件台账（`app/engine/ledger.py`）

- 只追加 JSONL，每行一个事件，写入后 `fsync`；序号严格递增。
- 事件先在状态副本上 `apply_event` 校验，再落盘，坏事件不会进入台账。
- 启动时重放全量事件；损坏/乱序/无法应用的行会被丢弃、原文件归档为 `*.corrupt-*`，并追加一条 `note(recovery)` 记录修复结果。
- `state_at(seq)` 可把任意历史前缀重放成状态，供回放视图使用（只读，不改台账）。

### 资源与预约（`app/engine/domain.py`）

- 资源分设备、准备间、记录间、人员四类，能力（capability）决定可执行步骤；资源版本随故障/班次调整单调递增。
- 检查按模板展开为多步骤资源链（准备 → 扫描 → 协议归档），每步同时占用一台设备和一名当班人员。
- 预约状态：`SCHEDULED / STARTED / COMPLETED / NO_SHOW / CANCELLED / UNSCHEDULED`；`STARTED/COMPLETED` 永久冻结。

### 排程计算（`app/engine/planner.py`）

- 贪心 + 多排序尝试：整体优化会尝试按优先级、截止、到达顺序、时长、稳定序等多组顺序各跑一次，取目标函数最优者。
- 目标函数按优先级加权等待（P1 权重 8、P2 4、P3 3、P4 2、其余 1），再叠加逾期、紧急最长等待、改期次数与完成时刻；`tie_break` 改变各项次序。
- 滚动局部调整只把 `movable` 集合内的既有预约视为可动，其余保持冻结；开启「顺延邻域」后按开始时间/优先级逐级扩大邻域（迭代加深），一旦主导入项可排即停。
- 方案里的 `bookings` 是「要写入的调整」，`frozen` 是不可动但仍属当日的既有预约；两者一起构成 `placed` 指标，改期次数只统计 `bookings` 中相对原时段的移动。
- 能力/班次缺失的检查不进入候选，而是直接进入未排列表并附带具体原因。

### 试算 / 确认（`app/engine/service.py`）

- 试算写入独立目录 `data/trials/<id>.json`（临时文件 + 原子替换），**从不写正式台账**。
- 确认时依次核对：
  1. `base_version` 不得超前于当前台账；
  2. 方案记录的每个资源版本 == 当前版本，且试算之后没有该资源的变更事件；
  3. 每个检查的签名（状态 / 准备 / 修订 / 日期）未变；
  4. 方案合法性：窗口、能力、人员角色、资源与人员互斥（含方案内部）、准备步骤必须早于扫描、不得早于当前时钟、已开始/完成的检查不得被移动。
- 任一失败都返回 `409` + 逐条 `conflicts`，台账保持不变。
- 并发：确认串行化（`_confirm_lock`）；并行试算各用同一不可变快照，若试算期间台账前进会给出提示。

### 中断与恢复

- 「模拟中断」会先写入 `status=running` 的检查点，再抛出中断；正式台账不受影响。
- 启动或点击「恢复状态」时：清掉写了一半的 `.tmp-*`、把 `running` 标记为 `interrupted`、把无法解析的试算文件改名为 `.broken` 隔离。
- 恢复后可从检查点重新试算。

## 测试

```bash
# 后端与 HTTP 集成测试 (纯标准库)
python3 -m unittest discover -s tests -v

# 浏览器端到端 (需要 Playwright + Chromium)
python3 tests/e2e_check.py http://127.0.0.1:8766
```

## 目录

```
app/
  server.py            标准库 HTTP 服务与静态文件
  engine/
    domain.py          资源/班次/模板/检查/预约/方案/状态
    feasibility.py     可用窗口、能力匹配、最早可行时段
    planner.py         整体优化与滚动局部调整
    ledger.py          事件台账、投影、损坏恢复、试算存储
    service.py         试算/确认/执行/回放/恢复
    demo.py            虚构演示数据
  static/              index.html / styles.css / app.js
tests/
  test_engine.py       台账、排程、确认、恢复
  test_api.py          HTTP 接口流程
  e2e_check.py         浏览器端到端检查
```
